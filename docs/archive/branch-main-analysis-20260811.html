一眼结论

这个分支不是普通的小修，而是一次“技能入口压缩 + PRD/设计职责拆分 + Canvas/表单/导航机器化约束”的大改。总体方向对强模型是正向的：入口更短、职责更清楚、CLI 和测试承担更多硬约束；但对弱模型存在一个核心风险：很多原来写在入口里的长流程被移动到 workflow/ 和 references/，弱模型如果少读一步，就会丢 PRD、设计、真实数据、导航或发布闭环。

主要新增了什么

主题关键文件变化影响
完整应用编排拆成三段 yida-requirement-analysis、yida-prd、yida-design、yida-app 先生成共享需求简报，再并行生成 prd.md 与 design.md；yida-design 不再写 PRD。 职责更清晰，减少一个技能既写业务又写视觉的混乱；但弱模型必须正确加载 3 个技能并做 join。
入口压缩与按需引用 yida-skills/SKILL.md、各子技能 SKILL.md 根入口从 288 行降到 133 行；yida-app 从 329 行降到 99 行；多个技能把复杂细则拆到 workflow/ 和 references/。 减少上下文噪音，让模型先路由；同时更依赖“按阶段读取引用文件”的执行纪律。
Canvas 页面硬门禁 lib/app/canvas-source-guard.js、tests/canvas-source-guard.test.js 检查按钮、搜索、筛选、Tab、分页、菜单、链接、可点击卡片等是否有真实事件；缺 import、空事件、伪可点击会被拦。 显著降低弱模型生成“看起来能点但实际没逻辑”的页面。
真实数据绑定校验 lib/app/canvas-binding-guard.js、tests/canvas-binding-guard.test.js 校验 APP_TYPE、FORM_UUIDS、FIELDS 是否静态、真实、与当前 schema 匹配，placeholder 字段会报错。 强制弱模型使用真实 appType/formUuid/fieldId，避免用前端假数据冒充。
Canvas 运行时桥与官方方法名 lib/app/runtime/canvas-runtime.js、canvas-yida-api-methods.js 统一提供 window.__OPENYIDA_RUNTIME__.yida / __OPENYIDA_YIDA_API__，内置 13 个宜搭 API 和主题注入。 减少弱模型手写 this.utils.yida、普通 JSX API 或错误桥接的概率。
原生表单脚手架 lib/app/scaffolds/form/form-schema-builder.js、form-runtime.js、form.form.json 用独立 .form.json 脚手架生成原生表单，校验 Divider、字段定义、表单运行时、主题和详情样式。 把原生表单和自定义页面分开，减少弱模型把表单写成 JSX 的错误。
导航排序变成完成条件 lib/core/command-manifest.js、lib/app/nav-group.js 新增 nav-group auto-order、plan 文件、readback 验证；完整应用要求 verification.matched=true。 从“发了页面就算完”收紧到“导航可用且顺序正确”。
弱模型真实轮测材料 docs/qwen-round-reports/*.html 新增 6 轮 Qwen/Qoder 报告，覆盖 Canvas、数据连接、seed、导航、健康检查、运行时崩溃等问题。 给后续优化提供真实失败样本，而不是只看静态文档。

主要去掉了什么

类型内容影响
删除文件 yida-design/workflow/step-1-positioning.md、yida-design/workflow/step-3-information-architecture.md 这两部分业务定位和信息架构职责从 yida-design 移走，转给 yida-requirement-analysis 和 yida-prd。旧路径不再可读。
职责迁移 yida-design/references/app/* 与 output-prd.md 移到 yida-prd PRD 不再是设计技能的副产物；路由或老习惯仍把“页面清单、导航规划”交给 yida-design 时会降级。
内联规则下沉 yida-app、yida-create-form-page、yida-process-rule、yida-formula、yida-integration 等大幅瘦身 复杂命令参数、流程 DSL、公式细节、集成节点示例不再默认塞进入口；弱模型不读取 reference 时会缺细节。
输出风格收敛 完整应用默认不再输出资源 ID 表、长 URL 列表、静态资源链接 用户体验更清爽；但排障场景需要模型知道什么时候额外补 ID 证据。
页面容器先建策略收紧 完整应用要求先完成 Canvas 源码和编译，再 create-page --source 并发布 减少空页面；弱模型如果还按旧链路批量创建空容器，会更容易被判未完成。

弱模型表现风险

风险等级为什么会变差已有缓解建议
入口变薄导致少读引用文件 高 当前 yida-app 明确要求执行前读取 workflow/resolve-context.md、workflow/build-stages.md、workflow/final-output.md。弱模型常见问题是读完入口就直接动手。 check:skills、技能契约测试、入口里重复写了“执行到每个阶段前先读取”。 给弱模型评测增加“未读 workflow 即动手”的负例；也可以考虑 CLI/manifest 输出当前阶段必读 reference 清单。
PRD 和设计拆分后路由混淆 高 main 里 yida-design 同时输出 PRD 和 design；现在页面清单、导航、资源蓝图归 yida-prd，视觉归 yida-design。弱模型或旧缓存容易沿用老路径。 路由场景已把“页面清单和导航分组”期望改为 yida-prd，并新增 yida-requirement-analysis 场景。 补一组低能力模型 routing eval：规划页面清单、只要视觉、完整应用、已有会议稿转 PRD 四类必须区分。
并行产物 join 容易漏 中高 yida-requirement-analysis 要写共享简报，然后 yida-prd 与 yida-design 同时读取。弱模型可能跳过 brief、只写其中一个文件，或两份文件不继承同一个 explicitScope。 yida-app 的核心边界写了两份文件完成后校验一致性；manifest 也输出 full_app_artifact_route。 增加一个机器校验：检查 prd.md、design.md、requirement-brief.json 的项目名、页面 key、explicitScope 是否一致。
薄 page-spec.json 让弱模型生成泛化页面 高 分支要求 page-spec.json 只记录 prdRefs/designRefs、真实资源和源码路径，不复制内容。弱模型如果只读 spec，不回读 PRD/design 原文，会做出模板味页面。 yida-canvas-custom-page 写明“按引用读取原文后实现”；page generation guide 和 guard 检查 content blocks。 在页面生成器/检查器里检测 page-spec 是否带 refs，源码是否声明并实现对应 @openyida-content-blocks。
严格 Canvas 守卫让弱模型更容易卡住 中 新增事件、import、数据绑定、运行时 API、content block、自动加载数据等硬规则。弱模型生成质量会提高，但失败后可能重复同一个命令或只改注释。 错误码更具体；Qwen 轮测已经暴露并修复 setError is not defined、seed 缺失等问题。 把守卫错误按 repairType 输出到技能文案：source/import/data/runtime/navigation，让弱模型知道下一步改哪里。
复杂子技能示例外移后，边缘能力下降 中 yida-formula 从 425 行到 59 行，yida-process-rule 从 455 行到 76 行，yida-integration 从 381 行到 69 行。复杂公式、流程 DSL、集成节点依赖 reference。 每个技能保留“何时读取”表，新增 process DSL、integration CLI options 等 reference。 对公式、流程、集成各补 2-3 个弱模型 golden case，要求模型必须引用对应 reference 后再产出。
导航完成条件变严 中 manifest 现在要求完整应用写 navigation-plan.json 并 verification.matched=true，warning 或 auto-order 不是完成。弱模型可能发布完页面就结束。 command-manifest 和 yida-app 都把导航计划列为完成条件。 在最终输出前增加固定检查项：publish 成功、nav readback matched、seed 证据或跳过原因。
浏览器能力不足时容易假报 PASS 中 Qwen 报告显示浏览器因 DingTalk 登录跳转无法完整验证时，必须标 UNKNOWN；弱模型容易把源码/API 证据写成浏览器通过。 Round 05/06 报告已经把 UNKNOWN 与 PASS 区分清楚。 把“浏览器不可验必须 UNKNOWN”加入发布/验收 skill 的完成条件和 eval rubric。

对弱模型也有正向影响的点

  • 入口压缩能减少一次性上下文负担，弱模型不再被几百行全流程说明淹没。
  • 运行时桥、表单脚手架、Canvas scaffold 把高频样板代码固化，弱模型只要扩展业务内容，不必从零写桥接。
  • Canvas 守卫、绑定守卫、页面编译路由和导航 readback 把“模型自觉”转成“机器检查”，能拦住弱模型常见假完成。
  • 6 轮 Qwen/Qoder 报告提供真实失败样本，后续优化有了可复现方向。
