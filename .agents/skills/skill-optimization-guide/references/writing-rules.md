# 写作规则

## 用途

步骤 3 逐文件改写时，用来指导每句话怎么写。

## 句式标准

每句话写成以下两种格式之一：

- **动作句**：对象 + 动作 + 产物。例："表单提交入口 PC 端用抽屉打开，移动端整页打开"。
- **条件句**：条件 → 动作。例："用户诉求是新建 skill → 交给 skill-create"。

## 用词表

### 推荐动词

读取、判断、输出、保持、复用、写入、交给、消费、发布、验证、列出、标记、合并、删除、移动。

### 禁止使用的抽象词

| 抽象词 | 替换为 |
|--------|--------|
| 胶水 | 列出具体放置的入口和组件 |
| 赋能 | 写清增加了什么字段、校验、查询或入口 |
| 闭环 | 写清从提交到审批到查看到统计的具体路径 |
| 一体化 | 写清用户从哪进入、完成什么操作、看到什么结果 |
| 中台 | 写清提供了什么 API、数据源或服务 |
| 高级/好看 | 写清主题色、布局、间距、图标、空态、加载态 |

### 禁止使用的过程词

考虑、感觉、为什么、后续、可以再、讨论、方案、临时、暂时。

## 正向引导规则

1. 先写"做什么"，这是主体。
2. 只在以下场景补充"禁止"：数据破坏、权限风险、资源误删、技能误选、发布虚假完成。
3. 把负向句改写为正向句的方法：找到"不要做 X"背后隐含的"应该做 Y"，写 Y。

| 负向写法 | 正向改写 |
|---------|---------|
| 不要在 PC 端 window.open | PC 端用抽屉 iframe 打开 |
| 不要把完整代码放入口 | 入口只放流程表和规则摘要，完整代码放 references |
| 避免重复描述 | 每条规则只在一处详细解释 |

## 代码去重标准

| 文件位置 | 允许的代码形式 |
|---------|--------------|
| SKILL.md | 零代码（只有 bash 单行命令和 API 端点速查） |
| workflow/*.md | 零代码或仅关键命令 |
| references/*.md | 骨架代码：函数签名 + 关键行注释，不含完整实现 |
| assets/ | 完整可执行代码或模板 |

## 铁律写法标准

铁律是 SKILL.md 中专门放高风险红线的章节。写法要求：

1. **只放真正会造成严重后果的操作**：数据丢失、权限越界、发布错误、资源误删。
2. **格式固定**："严禁 + 具体动作 + 后果或边界说明"。
3. **数量控制在 3-7 条**：多了说明没区分轻重，需要把非高风险的移到核心规则。
4. **和核心规则的区别**：核心规则是正向引导（应该怎么做），铁律是红线（绝对不能做）。

示例：

```markdown
## 铁律

1. **严禁未确认就删除用户数据**：任何删除操作必须先弹确认弹窗，用户点确认后才执行。
2. **严禁跳过权限校验直接调用后端接口**：所有 API 调用必须经过 auth middleware。
3. **严禁把 access_token 写入前端代码或日志**：token 只存 httpOnly cookie。
```

## 规则分级

技能中的规则分两级，用标签区分：

- **FATAL**：违反后代码崩溃或运行时报错。放在规则列表最前面。
- **IMPORTANT**：违反后代码能跑但有隐患（性能、体验、可维护性）。放在 FATAL 之后。
