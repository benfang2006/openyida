# 技能文档优化方法论（详细版）

> 本文档是 `skill-optimization-guide` 的参考文档，包含详细的操作步骤、分级标准、验证方法和反模式案例。

## 三层职责模型

```
SKILL.md（入口层）     → "怎么做" + "什么规则"（触发、作用域、流程、输出、参考导航）
workflow/*.md（步骤层）   → "每一步怎么完成"（较长且必须按顺序执行的流程）
references/*.md（规范层） → "查什么" + "怎么判定"（场景规则、参数表、决策矩阵、反模式）
assets/（素材层）        → 可复用素材、脚本输入或非默认实现材料
```

### 各层职责边界

| 层级 | 内容 | 不应包含 |
|------|------|---------|
| SKILL.md | frontmatter、定位、入口路由/作用域判断、标准流程、核心规则、输出/doneWhen、参考文档导航表 | 方案讨论、命名争论、历史复盘、未来拆分设想、完整代码示例、详细反模式解释、API 完整参数 |
| workflow/*.md | 标准流程的长步骤、每步输入/动作/产出、自检点 | 与入口重复的作用域判断、场景大全、方案讨论 |
| references/*.md | 规则的详细解释、场景参考、参数表、决策矩阵、代码骨架（非完整实现） | 与 SKILL.md 重复的规则摘要、可运行的完整页面 |
| assets/ | 可复用素材、脚本输入或辅助材料 | 默认执行流程和业务规则 |

## OpenYida Skill 目录约定

```text
yida-skills/skills/<skill-name>/
  SKILL.md
  workflow/
    step-1-*.md
    step-2-*.md
  references/
    scenes/*.md
    *.md
  sub_skill/<sub-name>/
    SKILL.md
  assets/
```

目录选择规则：

| 内容 | 推荐位置 | 判断标准 |
|------|----------|----------|
| 触发、作用域、流程总览、完成标准 | `SKILL.md` | agent 进入技能后必须马上知道 |
| 超过 4 步或单步超过 50 行的流程 | `workflow/step-*.md` | 必须按顺序执行，入口只列 Step 表 |
| 页面场景、主题规则、字段表、URL 表、故障处理 | `references/` | 只有特定场景才读取 |
| landing/dashboard/list/detail/workbench/screen 等页面场景 | `references/scenes/*.md` | 已有 scene 目录时继续收敛到这里，不再建重复平行目录 |
| 单页设计、批处理等内部独立子流程 | `sub_skill/<name>/SKILL.md` | 需要独立入口，但不需要成为顶层 skill |
| 可执行素材、脚本输入 | `assets/` | 输出时复用，不作为说明文档阅读 |

## SKILL.md 结构模板

```markdown
---
name: <skill-name>
description: <做什么；何时触发；输出什么>
---

# <skill-name>

一句话说明负责的对象和产物。

## 入口路由 / 作用域判断

| 用户诉求 | 判定为 | 唯一动作 |
| --- | --- | --- |

## 标准流程

| 步骤 | 名称 | 读取文件 | 动作 | 产出 |
| --- | --- | --- | --- | --- |

## 核心规则

1. **规则名**：正向动作 + 产物或边界。

## 输出 / doneWhen

- 输出文件：
- 完成证据：

## 参考文档

| 文档 | 覆盖范围 | 何时阅读 |
| --- | --- | --- |
```

写作原则：

- description 写给路由器，必须包含触发词和产物；body 不再单独堆一段"什么时候使用"。
- 作用域判断放入口，step 文件只写本步骤动作，避免每个步骤重复门槛。
- skill 只写执行合同；背景、过程推理和方案讨论放普通 docs / PRD / issue。
- 跨技能关系写成"本 skill 输出 X，另一个 skill 消费 X"。

## 规则分级标准

将所有规则合并为统一的"核心规则"章节，分两级：

- **FATAL**：违反后代码无法运行（语法错误、运行时崩溃、API 调用失败）
- **IMPORTANT**：违反后代码能运行但有隐患（性能、体验、可维护性）

```markdown
### 致命规则（FATAL）
违反会导致页面崩溃或运行时报错：
1. **规则名称**：一句话描述

### 重要规则（IMPORTANT）
影响代码质量和用户体验：
1. **规则名称**：一句话描述
```

## 代码去重规范

| 文件类型 | 应保留的代码形式 |
|---------|----------------|
| SKILL.md | 零代码（只有 bash 命令和 API 速查表） |
| references/*.md | 骨架代码（函数签名 + 注释说明，不含完整实现） |
| assets/ | 可复用素材或脚本输入 |

### 去重操作

1. references 中的完整代码 → 精简为骨架，保留关键函数签名和使用说明
2. 多个 references 文件间的重复代码 → 保留在最相关的那个文件中，其他改为引用
3. assets/ 中的脚本或素材必须自检：是否仍符合当前 skill 的规则

## 语言与引导规范

Skill 面向下一次执行任务的 agent，不面向读方案的人。每句话都应能变成动作、判断或产物。

| 写法 | 推荐 | 原因 |
|------|------|------|
| "完整应用由 yida-design 输出产品设计文档；yida-app 消费该文档创建资源" | 是 | 清楚描述协作合同 |
| "自定义页放置表单提交入口、流程处理入口、报表查看入口和详情页入口，用户能在当前页查看数据并继续操作" | 是 | 用具体入口和用户动作解释页面职责 |
| "自定义页负责展示、洞察、入口、详情和胶水" | 否 | "胶水"是比喻，新手不知道要做什么 |
| "为什么不是放在 yida-app：因为..." | 否 | 这是方案讨论，不是执行规则 |
| "PC 端用抽屉 iframe 承载原始提交 URL，移动端整页打开" | 是 | 正向动作清晰 |
| "不要在 PC 端 window.open" | 谨慎 | 可作为高风险补充，但不要成为主表达 |
| "如果后续发现过大可以再拆" | 否 | 未来规划会干扰当前路由 |
| "这个设计是为了避免..." | 否 | 原因可放 docs，skill 写最终规则 |

语言规则：

1. 优先使用正向动词：读取、判断、输出、保持、复用、写入、交给、消费、发布、验证。
2. 控制负向句：只有数据破坏、权限风险、资源误删、技能误选、发布虚假完成等高风险边界才写"禁止/不要"。
3. 使用直白业务话：每段优先写成"对象 + 动作 + 产物"，例如"表单提交入口 PC 用抽屉打开，移动端整页打开"。
4. 避免过程词：考虑、感觉、为什么、后续、可以再、讨论、方案、临时、暂时。
5. 避免小白难懂的抽象词、比喻和内部黑话，例如"胶水/赋能/一体化/闭环/中台/增强"；需要表达时改成具体资源、操作和结果。
6. 避免把同一规则在入口、step、reference 反复写；入口留摘要，细节放一个权威文件。

### 抽象词改写规则

| 抽象写法 | 改成 |
|---------|------|
| 胶水 | 放置表单提交入口、流程处理入口、报表查看入口、详情页入口和导航入口 |
| 能力增强 | 增加字段、校验、数据查询、页面入口或发布流程 |
| 闭环 | 写清从提交、审批、查看到统计的具体路径 |
| 一体化体验 | 写清用户从哪个入口进入、完成哪个操作、看到哪个结果 |
| 高级 / 好看 | 写清主题色、布局、间距、层级、图标、空态、加载态和错误态 |

## 参考文档导航表规范

SKILL.md 末尾必须有完整的参考文档导航表：

```markdown
## 参考文档

| 文档 | 覆盖范围 | 何时阅读 |
|------|---------|---------|
| [编码指南](references/coding-guide.md) | 规范详解 | 编写代码前必读 |
| [宜搭 API](../../references/yida-api.md) | API 完整参数 | 调用 API 前必读 |
```

检查清单：
- 所有 references/ 下的文件都在表中
- 跨 skill 共享文档（yida-api.md、model-api.md）也在表中
- "何时阅读"列有明确指引（"必读" vs "按需"）
- 所有链接路径正确（特别注意相对路径层级）

## 模拟大模型阅读验证

优化完成后，让 AI 按以下顺序完整读取所有文档，输出评估报告：

1. 读取 SKILL.md（入口）
2. 按参考文档表顺序，逐个读取所有外链文档
3. 按需读取 assets/ 中的素材或脚本输入
4. 读取跨 skill 共享文档（yida-api.md 等）

### 评估维度

| 维度 | 检查项 |
|------|--------|
| 信息流 | 阅读顺序是否层层递进、无断裂？ |
| 冗余度 | 任意两文件重叠率是否 ≤ 15%？ |
| 一致性 | 规则数、规则内容、代码示例是否三者对齐？ |
| 自包含 | 仅读 SKILL.md 能否开始开发？ |
| 链接正确 | 所有相对路径是否可达？ |

### 问题分级

- **P0**：逻辑错误、规则遗漏、数字不匹配 → 必须修复
- **P1**：显著冗余、信息不一致、关键链接缺失 → 应该修复
- **P2**：措辞优化、格式统一、注释完善 → 可选修复

## 常见反模式

| 反模式 | 正确做法 | 实际案例 |
|--------|---------|---------|
| SKILL.md 内联完整代码 | 保留步骤说明，完整实现放到 reference 或正式源码 | SKILL.md 从 610 行降到 174 行 |
| 多个章节重复同一规则 | 合并为"核心规则"统一章节 | 4 个约束章节合并为 1 个 |
| references 包含完整实现 | 精简为骨架，完整版放正式源码或专门资产 | coding-guide 87 行模板精简为 25 行 |
| 规则数声称与实际不符 | 交叉验证确保严格对齐 | "17 条"实际是 18 条 |
| 示例模板违反自身规范 | 模板必须自检合规 | template.js 有 3 个违规 bug |
| 流程指引单独成文件 | 内容少于 50 行直接合并到 SKILL.md | examples.md 43 行合并到快速开始 |
| 参考文档表缺少共享文档 | 补全所有相关文档（含跨 skill 共享） | 缺少 yida-api.md 和 model-api.md |
| 链接路径层级错误 | 仔细核对相对路径 | `./yida-api.md` 应为 `../../../references/yida-api.md` |

## 优化效果参考

以 yida-custom-page 为例：

| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| SKILL.md 行数 | 610 | 174 |
| 文件数量 | 4 个文档 + 1 个模板 | 2 个文档 + 1 个模板 |
| 三文件代码重叠率 | ~70% | ~12% |
| 规则数对齐 | 不一致（17 vs 18） | 严格一致（18 = 18） |
| 模板合规性 | 3 个违规 bug | 0 违规 |
| 参考文档导航 | 缺少 2 个共享文档 | 完整覆盖 |
